# Резервное копирование и восстановление БД

Схема такая же, как в серьёзных продакшн-установках PostgreSQL: физические бэкапы
через pgBackRest, непрерывный архив WAL, восстановление на точку во времени (PITR),
шифрование на клиенте, автопроверка восстановления и алерты по свежести.
Репозиторий бэкапов — Cloudflare R2.

## Цели

| Метрика | Значение | За счёт чего |
| --- | --- | --- |
| RPO (допустимая потеря данных) | ≈ 1 минута | `archive_timeout=60` + непрерывный archive-push |
| RTO (время восстановления) | десятки минут | full + один diff, без длинных цепочек incr |
| Окно PITR | ≈ месяц | 4 полных бэкапа с недельным интервалом |
| Проверка восстановления | раз в неделю, автоматически | `scripts/pgbackrest-verify-restore.sh` |

Цифры RPO/RTO — расчётные. Фактические появятся только после первых учений
(см. «Учения» ниже) — измерьте и впишите реальные значения в эту таблицу.

## Из чего состоит

| Файл | Зачем |
| --- | --- |
| `postgres/Dockerfile` | PostgreSQL 16 + pgbackrest в одном образе |
| `postgres/pgbackrest.conf` | конфиг без секретов (ретеншен, сжатие, шифрование, stanza) |
| `docker-compose.backup.yml` | включает архив WAL и добавляет сайдкар `pgbackrest` |
| `scripts/pgbackrest-scheduler.sh` | расписание: full/diff, проверки, логические дампы |
| `scripts/pgbackrest-health.sh` | свежесть бэкапов, живость архива WAL, размер `pg_wal`, алерты |
| `scripts/pgbackrest-verify-restore.sh` | восстанавливает бэкап в копию и проверяет данные SQL-запросами |
| `scripts/pgbackrest-pitr.sh` | восстановление боевой БД на точку во времени |
| `scripts/backup-db.sh`, `scripts/restore-db.sh` | логические дампы вручную (аварийный выход) |

Логические дампы `pg_dump` оставлены сознательно: они решают три задачи, которые
физические бэкапы не решают вообще: восстановить одну таблицу, переехать на
другую мажорную версию PostgreSQL и выжить, если повреждён сам репозиторий pgBackRest.

## Настройка Cloudflare R2

1. Создать **отдельный бакет** только под бэкапы БД, например `devprep-db-backup`.
   Не кладите их в тот же бакет, что медиа (`docs/media.md`).
2. В токенах R2 создать **отдельный API-токен** с доступом *Object Read & Write*
   только к этому бакету. Не переиспользовать `S3_ACCESS_KEY` от медиа.
3. Взять S3-эндпоинт вида `https://<ACCOUNT_ID>.r2.cloudflarestorage.com`.
4. Включить в настройках бакета блокировку удаления (bucket lock / retention) на 30 дней,
   если она доступна в вашем плане. Это единственная защита от сценария
   «взломали сервер и удалили бэкапы тем же токеном». Набор функций R2 меняется —
   сверьтесь с текущей панелью.
5. Сгенерировать пароль шифрования: `openssl rand -base64 48`.

Особенности R2, уже учтённые в конфиге:

- `repo1-s3-uri-style=path` — R2 работает только с path-style URI;
- `BACKUP_S3_REGION=auto` — единственный регион, который принимает R2 (значение по умолчанию);
- `repo1-bundle=y` и `repo1-block=y` — мелкие файлы склеиваются в пачки, так что
  число операций class A и счёт за R2 остаются маленькими;
- исходящий трафик в R2 бесплатный, поэтому еженедельные проверки восстановления
  не бьют по бюджету (в отличие от AWS S3).

### Главное ограничение этого варианта

Медиа и бэкапы БД теперь у одного провайдера. Если аккаунт Cloudflare
заблокируют или угонят, можно потерять и то и другое сразу. Минимум — отдельный
бакет и отдельный токен (выше). Сильнее — отдельный аккаунт Cloudflare только
под бэкапы.

Чтобы закрыть риск совсем, раз в неделю увозите очередной логический дамп из
`./backups` за пределы Cloudflare — достаточно одного `scp` на другой диск или
в любое другое хранилище. Это даст холодную копию с RPO в неделю против
катастрофы уровня провайдера.

### Переменные окружения

Обязательные (без них `docker compose` не стартует — это специально):

| Переменная | Описание |
| --- | --- |
| `BACKUP_S3_BUCKET` | имя R2-бакета для бэкапов |
| `BACKUP_S3_ENDPOINT` | `https://<ACCOUNT_ID>.r2.cloudflarestorage.com` |
| `BACKUP_S3_ACCESS_KEY` | Access Key ID токена R2 для этого бакета |
| `BACKUP_S3_SECRET_KEY` | Secret Access Key того же токена |
| `BACKUP_CIPHER_PASS` | пароль шифрования репозитория |

Необязательные:

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `BACKUP_S3_REGION` | `auto` | для R2 не менять |
| `BACKUP_TICK_SECONDS` | `86400` | интервал между бэкапами |
| `BACKUP_FULL_INTERVAL_DAYS` | `7` | как часто делать полный бэкап |
| `BACKUP_VERIFY_INTERVAL_DAYS` | `7` | как часто проверять восстановление |
| `BACKUP_LOGICAL_INTERVAL_DAYS` | `7` | как часто делать `pg_dump` в `./backups` |
| `BACKUP_LOGICAL_KEEP` | `4` | сколько логических дампов хранить |
| `BACKUP_MAX_AGE_HOURS` | `30` | порог алерта по возрасту бэкапа |
| `BACKUP_WAL_MAX_AGE_MINUTES` | `15` | порог алерта по архивации WAL |
| `BACKUP_PGWAL_MAX_MB` | `4096` | порог алерта по размеру `pg_wal` |
| `BACKUP_ALERT_WEBHOOK` | — | HTTP-эндпоинт для алертов |
| `VERIFY_MAX_DATA_AGE_DAYS` | `0` (выкл) | проверять свежесть `question.updated_at` |

Пример блока для `.env`:

```env
BACKUP_S3_BUCKET=devprep-db-backup
BACKUP_S3_ENDPOINT=https://xxxxxxxxxxxxxxxxxxxxxxxx.r2.cloudflarestorage.com
BACKUP_S3_ACCESS_KEY=...
BACKUP_S3_SECRET_KEY=...
BACKUP_CIPHER_PASS=...
BACKUP_ALERT_WEBHOOK=
```

## Запуск

```bash
# каталог для логических дампов — под uid postgres из образа
mkdir -p backups && sudo chown 999:999 backups

docker compose -f docker-compose.yml -f docker-compose.backup.yml up -d --build
docker compose -f docker-compose.yml -f docker-compose.backup.yml logs -f pgbackrest
```

Оба файла нужно передавать каждый раз, включая `restart` и `down`. Удобно зафиксировать
это в окружении сервера:

```bash
export COMPOSE_FILE=docker-compose.yml:docker-compose.backup.yml
```

Первый запуск сам создаёт stanza, проверяет доступ к репозиторию и делает полный бэкап.

## Повседневные команды

```bash
# состояние репозитория и список бэкапов
docker compose exec pgbackrest pgbackrest --stanza=devprep info

# сквозная проверка конфига и архивации WAL
docker compose exec pgbackrest pgbackrest --stanza=devprep check

# внеплановый полный бэкап (например, перед миграцией)
docker compose exec pgbackrest pgbackrest --stanza=devprep --type=full backup

# здоровье бэкапов (то же, что гоняет шедулер)
docker compose exec pgbackrest bash /opt/backup/pgbackrest-health.sh

# проверка восстановления на копии; боевую БД не трогает
docker compose exec pgbackrest bash /opt/backup/pgbackrest-verify-restore.sh
```

## Ранбуки

### 1. Восстановление на точку во времени (удалили лишнее, сломала миграция)

Сначала — найти момент до аварии и проверить его на копии, не трогая боевую базу:

```bash
docker compose exec pgbackrest bash -c '
  pgbackrest --stanza=devprep --pg1-path=/var/tmp/verify/data \
    --type=time --target="2026-09-02 18:30:00+03" --target-action=promote \
    --archive-mode=off restore'
```

Если точка верная — применить к боевой БД (скрипт гасит `api`/`web`, восстанавливает,
поднимает обратно):

```bash
./scripts/pgbackrest-pitr.sh '2026-09-02 18:30:00+03'
```

После promote начинается новая timeline — обязательно сделать полный бэкап сразу после.

### 2. Полная потеря сервера

1. Поднять новый сервер, положить репозиторий кода и `.env` (секреты из менеджера паролей).
2. `docker compose -f docker-compose.yml -f docker-compose.backup.yml up -d --build postgres`
   — база поднимется пустой, её надо остановить: `docker compose stop postgres`.
3. `./scripts/pgbackrest-pitr.sh latest` — восстановит максимально возможное состояние.
4. Проверить вход админа (`docs/admin-recovery.md`) и медиа (`docs/media.md`).
5. Сделать полный бэкап новой timeline.

### 3. Нужна одна таблица или несколько строк

Физический бэкап так не умеет — берём логический дамп из `./backups` или поднимаем
копию через `pgbackrest-verify-restore.sh`, потом копируем нужное вручную:

```bash
pg_restore --data-only --table=question -d devprep backups/devprep-20260902-000000.dump
```

## Ключи и секреты

Бэкап без ключей — не бэкап. Вне сервера (менеджер паролей) должны храниться:

- `BACKUP_CIPHER_PASS` — без него репозиторий невосстановим. Совсем.
- `BACKUP_S3_ACCESS_KEY` / `BACKUP_S3_SECRET_KEY` — доступ к репозиторию.
- `TOTP_ENC_KEY` и `JWT_SECRET` — в бэкапе БД их нет. Без `TOTP_ENC_KEY` восстановленные
  TOTP-секреты админов не расшифруются и второй фактор придётся сбрасывать
  (`docs/admin-recovery.md`).
- `MEILI_MASTER_KEY` — индекс Meilisearch не бэкапится сознательно: он полностью
  перестраивается из БД.

## Алерты

Проверка здоровья гоняется после каждого бэкапа и орёт, если:

- бэкап старше `BACKUP_MAX_AGE_HOURS`;
- WAL не архивировался дольше `BACKUP_WAL_MAX_AGE_MINUTES`;
- `pg_wal` больше `BACKUP_PGWAL_MAX_MB` (симптом сломанного `archive_command`);
- `pgbackrest check` не прошёл;
- восстановление давно не проверялось или проверка провалилась.

Алерт идёт в `stderr` (видно в `docker compose logs pgbackrest`) и, если задан
`BACKUP_ALERT_WEBHOOK`, POST-ом в виде JSON:

```json
{
  "service": "devprep-db-backup",
  "stanza": "devprep",
  "severity": "error",
  "subject": "WAL не архивируется",
  "detail": "последний успешный push 42 мин назад, порог 15 мин",
  "text": "..."
}
```

Поле `text` сразу подходит для Slack-вебхука. Для Telegram/PagerDuty/Alertmanager нужен
тонкий прокси-скрипт. Конкретный провайдер в код не вшит специально: половинчатая
интеграция с алертингом опаснее явного отсутствия.

**Без настроенного `BACKUP_ALERT_WEBHOOK` система остаётся молчаливой**: проблемы будут
в логах, которые никто не читает. Это главный незакрытый пункт при внедрении.

## Риски, о которых надо знать

1. **Сломанный `archive_command` может остановить базу.** С `archive_mode=on` PostgreSQL
   хранит WAL до успешной отправки. Если R2 недоступен долго, `pg_wal` растёт,
   и при заполнении диска база встанёт. Меры: `archive-async=y`, алерт по размеру
   `pg_wal`, запас свободного места на диске не меньше нескольких ГБ.
   Сознательно **не** включён `archive-push-queue-max`: он спасает диск ценой тихого
   выбрасывания WAL, то есть ломает PITR незаметно. Лучше алерт, чем тишина.
2. **Бэкапы и медиа в одном Cloudflare.** См. «Главное ограничение» выше: нужны
   отдельный бакет, отдельный токен и желательно холодная копия вне Cloudflare.
3. **Медиа и БД откатываются независимо.** После PITR возможны ссылки на ещё не
   загруженные файлы или осиротевшие объекты в R2. См. `docs/media.md`.
4. **Обновление мажорной версии PostgreSQL** требует `stanza-upgrade` и нового полного
   бэкапа; старые физические бэкапы на новую версию не восстанавливаются.
5. **`./backups` лежит на том же сервере.** Это удобство, а не защита; пока дамп не
   увезён с машины, он не считается копией.

## Учения

Автоматическая проверка еженедельно подтверждает, что бэкап восстанавливается и данные
в нём связные. Она не заменяет учения руками:

| Частота | Что делаем |
| --- | --- |
| перед выводом в бой | PITR на произвольную точку, замер RTO |
| раз в квартал | полное восстановление на чистом сервере с нуля, только по этому документу |
| раз в год | проверка доступности ключей у второго человека в команде |

Первые учения обязательны: до них система описана и настроена, но не доказана.
