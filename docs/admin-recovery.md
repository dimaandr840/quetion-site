# Восстановление доступа к админке

Админка защищена паролем и обязательным TOTP (2FA, Google Authenticator).
Здесь — что делать, если доступ потерян. Способы отсортированы от самого простого
к самому тяжёлому.

Резервных кодов (backup codes) больше нет: их роль полностью выполняет одноразовый
код из письма (уровень 1). Старая таблица `user_backup_code` удаляется миграцией
`010-password-reset.yaml`.

## Уровень 1. Забыт пароль или потерян телефон — сброс по почте

На странице входа есть ссылка «Забыли пароль или потеряли телефон?» → `/login/reset`.
Сценарий в два шага:

1. `POST /api/auth/password/reset/request` — человек вводит адрес почты. Если адрес
   совпал с адресом включённой учётки — на неё уходит одноразовый код `XXXX-XXXX`.
2. `POST /api/auth/password/reset/confirm` — код из письма и новый пароль
   (минимум 10 символов). При успехе отзываются все сессии, снимается блокировка,
   а при `PASSWORD_RESET_RESET_TOTP=true` (по умолчанию) стирается привязка
   аутентификатора — новый секрет выдаётся на следующем входе.

### Адрес почты нигде не раскрывается

Это требование, а не деталь реализации:

- ответ шага 1 содержит только `expiresInMinutes` — ни адреса, ни его маски,
  ни признака того, было ли отправлено письмо;
- ответ одинаков (202) для существующего и несуществующего адреса, поэтому форма
  не работает как проверка существования аккаунтов;
- ошибки шага 2 всегда один и тот же текст «Неверный или истекший код»;
- ни адрес, ни код не попадают в логи (даже в текст ошибки SMTP — логируется
  только класс исключения);
- в UI нет ни адреса, ни подсказки вида `d****@g****.com`.

### Защита от перебора и злоупотреблений

- код — 8 символов из алфавита 32 (без похожих `0/O`, `1/I`) → 2^40 вариантов;
- в БД хранится только BCrypt-хеш кода (cost 12) — дамп базы кодов не выдаёт;
- код одноразовый и живёт `PASSWORD_RESET_TTL` (по умолчанию 15 минут);
- активный код всегда ровно один: новый запрос гасит предыдущие;
- 5 неверных вводов (`PASSWORD_RESET_MAX_ATTEMPTS`) аннулируют код целиком;
- пауза между письмами `PASSWORD_RESET_COOLDOWN` (1 минута) — чтобы форма не стала
  бесплатным отправщиком писем;
- неудачные попытки пишутся в тот же журнал, что и попытки входа, поэтому
  работает общий IP-лимит `LOGIN_RATE_LIMIT_*` (20 неудач за 10 минут);
- просроченные коды чистит регламентная задача `SecurityMaintenanceJob`.

### Что нужно настроить

Без SMTP сервис запускается как обычно, но письма не уходят (в логе останется
ошибка о ненастроенном SMTP).

| Переменная | Зачем |
| --- | --- |
| `SMTP_HOST`, `SMTP_PORT` | адрес почтового релея (по умолчанию порт 587) |
| `SMTP_USERNAME`, `SMTP_PASSWORD` | учётка для SMTP AUTH |
| `SMTP_STARTTLS` | STARTTLS, по умолчанию `true` |
| `PASSWORD_RESET_MAIL_FROM` | адрес в поле From. Пусто — письма не отправляются |
| `PASSWORD_RESET_ENABLED` | `false` полностью закрывает публичный сброс |
| `PASSWORD_RESET_TTL` | срок жизни кода, по умолчанию `PT15M` |
| `PASSWORD_RESET_COOLDOWN` | пауза между письмами, по умолчанию `PT1M` |
| `PASSWORD_RESET_MAX_ATTEMPTS` | лимит вводов кода, по умолчанию 5 |
| `PASSWORD_RESET_RESET_TOTP` | стирать ли привязку 2FA при успешном сбросе |

Важно понимать риск: при `PASSWORD_RESET_RESET_TOTP=true` доступ к почтовому ящику
админа становится единственным фактором восстановления. Если это неприемлемо —
выставьте `false`, тогда сброс меняет только пароль, а 2FA сбрасывается только
с сервера (уровень 3).

## Уровень 2. Помощь второго администратора

Если почта недоступна (ящик утерян, SMTP не настроен) — пусть второй
администратор зайдёт и поможет. Второй админ — самая дешёвая страховка.

## Уровень 3. Аварийная команда (потеряно всё)

Пароль забыт, телефон потерян, почта недоступна. Подтверждением владения
системой считается доступ к серверу. На сервере:

```bash
docker compose run --rm --no-deps api \
  java -jar /app/app.jar \
  --recovery.email=admin@example.com \
  --recovery.password='новый-очень-длинный-пароль' \
  --recovery.reset-totp=true
```

Команда запускает приложение, выполняет восстановление, выводит результат в лог и
завершается (HTTP-порт в этом режиме не поднимается надолго).

| Аргумент | Зачем |
| --- | --- |
| `--recovery.email=` | Обязателен. Без него режим восстановления не включается вовсе |
| `--recovery.password=` | Новый пароль (минимум 10 символов). Если пользователя нет — будет создан админ |
| `--recovery.reset-totp=true` | Стирает привязку аутентификатора: на следующем входе выдастся новый секрет |
| `--recovery.unlock=false` | Отменяет автоснятие блокировки и сброс счётчика попыток (по умолчанию снимает) |

Любое действие необязательно: можно сбросить только 2FA или только пароль. После
любого восстановления все активные сессии отзываются.

**Гигиена после восстановления:**

- факт сброса попадает в лог — учитывайте это при разборе инцидентов;
- не оставляйте аргументы `--recovery.*` в постоянной команде запуска сервиса;
- пароль передан в командной строке — почистите history оболочки.

## Уровень 4. Прямой SQL (последний вариант)

Если приложение не запускается, но база жива:

```bash
docker compose exec postgres psql -U devprep -d devprep
```

```sql
-- снять привязку 2FA (на следующем входе выдастся новый секрет)
UPDATE app_user
   SET totp_secret = NULL, totp_enabled = false, totp_last_used_step = NULL
 WHERE email = 'admin@example.com';

-- снять блокировку после неудачных попыток
UPDATE app_user
   SET failed_login_attempts = 0, lockout_until = NULL
 WHERE email = 'admin@example.com';

-- отозвать все сессии
UPDATE refresh_token SET revoked_at = now() WHERE revoked_at IS NULL;

-- аннулировать все выданные коды восстановления
DELETE FROM password_reset_token;
```

Пароль через SQL напрямую менять нельзя: нужен BCrypt-хеш. Используйте уровень 3.

## Профилактика

- Заведите второго администратора на другом устройстве.
- Проверьте, что SMTP действительно работает: без него уровень 1 недоступен,
  и останется только консоль сервера.
- Держите TOTP-секрет в менеджере паролей с синхронизацией (1Password,
  Bitwarden), а не только в приложении на одном телефоне.
- Защитите почтовый ящик админа своим 2FA: теперь это канал восстановления доступа.
- Сделайте резервную копию `TOTP_ENC_KEY`: без него секреты 2FA в базе не
  расшифровать, и всем админам придётся перепривязывать аутентификатор.
