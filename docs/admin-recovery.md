# Восстановление доступа к админке

Админка защищена паролем и обязательным TOTP (2FA, Google Authenticator).
Здесь — что делать, если доступ потерян. Способы отсортированы от самого простого
к самому тяжёлому.

## Уровень 1. Потерян телефон — резервный код

На шаге ввода кода вместо шести цифр можно ввести резервный код вида
`XXXX-XXXX-XXXX` — тот же эндпоинт `POST /api/auth/totp/verify`.

- код одноразовый: после успешного входа он гаснет;
- в БД хранится только BCrypt-хеш — дамп базы кодов не выдаёт;
- счётчик остатка: `GET /api/auth/backup-codes`;
- новый набор (10 кодов, старые аннулируются): `POST /api/auth/backup-codes`.

### Почему резервные коды нельзя перебрать

Код — 12 символов из алфавита 32 (без похожих `0/O`, `1/I`), то есть
32^12 = 2^60 вариантов. При 10 действующих кодах шанс угадать с одного раза —
около 1 к 10^17. Сверху работают те же ограничения, что и для пароля:

- неверный резервный код — это такая же неудачная попытка: 5 подряд — блокировка
  учётки на 15 минут (`LOCKOUT_*`);
- 20 неудач с одного IP за 10 минут — IP отсекается (`LOGIN_RATE_LIMIT_*`);
- шаг ввода кода доступен только по короткоживущему mfa-токену, то есть после
  верного пароля;
- сравнение идёт через BCrypt (cost 12) — около 250 мс на попытку.

В сумме онлайн-перебор бессмыслен: он упирается в блокировку задолго до того, как
станет статистически значимым. Реальный риск резервных кодов — не перебор, а
хранение: скриншот в галерее или файл `codes.txt` на рабочем столе. Держите их в
менеджере паролей.

## Уровень 2. Забыт пароль

Публичного «Забыли пароль?» в админке нет, и это осознанное решение: такая форма —
ещё один вектор атаки (перебор email, подделка писем, угон почты) для аккаунта с
полными правами.

Варианты:

1. Если есть второй администратор — пусть он зайдёт и поможет. Второй админ — самая
   дешёвая страховка.
2. Иначе — аварийная команда на сервере (уровень 3).

## Уровень 3. Аварийная команда (потеряно всё)

Пароль забыт, телефон потерян, резервных кодов нет. Подтверждением владения
системой считается доступ к серверу. На сервере:

```bash
docker compose run --rm --no-deps api \
  java -jar /app/app.jar \
  --recovery.email=admin@example.com \
  --recovery.password='новый-очень-длинный-пароль' \
  --recovery.reset-totp=true \
  --recovery.new-codes=true
```

Команда запускает приложение, выполняет восстановление, выводит результат в лог и
завершается (HTTP-порт в этом режиме не поднимается надолго).

| Аргумент | Зачем |
| --- | --- |
| `--recovery.email=` | Обязателен. Без него режим восстановления не включается вовсе |
| `--recovery.password=` | Новый пароль (минимум 10 символов). Если пользователя нет — будет создан админ |
| `--recovery.reset-totp=true` | Стирает привязку аутентификатора: на следующем входе выдастся новый секрет |
| `--recovery.new-codes=true` | Выпускает новые резервные коды и печатает их в лог |
| `--recovery.unlock=false` | Отменяет автоснятие блокировки и сброс счётчика попыток (по умолчанию снимает) |

Любое действие необязательно: можно сбросить только 2FA или только пароль. После
любого восстановления все активные сессии отзываются.

**Гигиена после восстановления:**

- коды и факт сброса попадают в лог — очистите логи или выпустите коды заново
  через UI;
- не оставляйте аргументы `--recovery.*` в постоянной команде запуска сервиса;
- пароль передан в командной строке — почистите history оболочки.

## Уровень 4. Прямой SQL (последний вариант)

Если приложение не запускается, но база жива:

```bash
docker compose exec postgres psql -U devprep -d devprep
```

```sql
-- снять привязку 2FA (на следующем входе выдастся новый секрет)
UPDATE app_user
   SET totp_secret = NULL, totp_enabled = false, totp_last_used_step = NULL
 WHERE email = 'admin@example.com';

-- снять блокировку после неудачных попыток
UPDATE app_user
   SET failed_login_attempts = 0, lockout_until = NULL
 WHERE email = 'admin@example.com';

-- отозвать все сессии
UPDATE refresh_token SET revoked_at = now() WHERE revoked_at IS NULL;
```

Пароль и резервные коды через SQL напрямую менять нельзя: нужен BCrypt-хеш.
Используйте уровень 3.

## Профилактика

- Заведите второго администратора на другом устройстве.
- Держите TOTP и резервные коды в менеджере паролей с синхронизацией (1Password,
  Bitwarden), а не только в приложении на одном телефоне.
- Следите за счётчиком остатка кодов и выпускайте новый набор, когда осталось 3 или
  меньше (признак `lowOnCodes` в ответе `GET /api/auth/backup-codes`).
- Сделайте резервную копию `TOTP_ENC_KEY`: без него секреты 2FA в базе не
  расшифровать, и всем админам придётся перепривязывать аутентификатор.
